Published-system editing

A low-fidelity review of entering an edit, publishing changes, discarding a draft, resolving conflicts, and stopping an unchanged edit while the current system remains live.

9 screens Desktop + mobile Lo-fi · monochrome Click any wireframe to zoom
Flow

One private draft, three exits

Publishing updates the live system, discarding preserves the existing system, and an unchanged draft can stop editing without destructive confirmation.

Step 1 · Entry

Owner list

The row exposes the dual state clearly: a private edit exists while the published system remains live.

Annotations

  1. Visible editing status and published continuity.
  2. Continue editing is the single visible draft entry.
  3. The menu contains only Discard and Delete, separated by scope.
Why: the system name already opens the published version, so neither destination is repeated in the menu.
Step 2 · Review

Editing workspace

The existing preview-left and sticky-sidebar-right layout gains one persistent editing context and draft-specific labels.

Annotations

  1. The header carries the published-live reassurance once.
  2. The draft preview is visually unchanged.
  3. Publishing follows validation and rights confirmation.
  4. Agent access remains secondary and concise.
Step 3A · Publish

Publish conflict

A durable conflict replaces stale controls and requires reviewing the latest draft before another attempt.

Annotations

  1. The published-live reassurance remains visible.
  2. The latest draft remains available for review.
  3. No toast or automatic retry.
Step 3A · Complete

Publish success

The existing published state replaces editing controls and offers the updated system as the primary destination.

Annotations

  1. Editing context and draft actions are gone.
  2. Success replaces editing controls.
  3. Primary destination is the updated system.
Step 3B · Discard

Discard confirmation

The dialog names what will be lost, what will survive, and what happens to agent access.

Annotations

  1. Cancel receives initial focus.
  2. Discard never uses Delete language.
  3. The live system is explicitly preserved.
Step 3B · Conflict

Discard conflict

If the draft changes while the dialog is open, the owner must review it rather than blindly retrying.

Annotations

  1. The conflict stays in the dialog context.
  2. Review draft is the primary recovery action.
  3. The public system remains unchanged.
Step 3B · Complete

Discard success

Discard returns directly to the published system with a persistent inline confirmation.

Annotations

  1. One inline message confirms discard and ended access.
  2. The owner is already at the surviving published system.
  3. No intermediate success screen is introduced.
Step 3C · No changes

Stop editing

When the draft matches the published system, destructive language and confirmation disappear.

Annotations

  1. No Publish action appears.
  2. Stop editing is non-destructive.
  3. No confirmation is required.
Responsive · Mobile

Review before publishing

The mobile reading order keeps context first, then the draft, validation, publishing, and agent access.

Annotations

  1. Discard remains visible without becoming sticky.
  2. The draft precedes validation and publishing.
  3. Agent access remains last.
Why: the owner should inspect the proposed version before encountering the final action.
For review

UX guarantees retained

  • Draft and published states remain visibly distinct throughout editing.
  • Publish, discard, stop editing, and permanent deletion keep distinct labels and consequences.
  • Publish and discard conflicts require review instead of retrying unseen changes.
  • Discard and stop editing explicitly end agent access.
  • Publish success remains inline; discard returns directly to the surviving published system.
  • No-change editing ends without destructive language or confirmation.
  • Focus moves to headings, conflicts, previews, and safe dialog actions as defined in the UX analysis.
  • Mobile keeps review before publish, with no sticky action bar or added animation.
Low-fidelity wireframes use monochrome UI, 1.5px strokes, an 8px grid, and red dashed annotations only for reviewer callouts.
